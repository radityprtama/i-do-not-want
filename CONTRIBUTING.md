# Contributing

Thanks for helping make vibecoded software slightly less terrifying.

## What makes a good check?

Every proposed check should define five things:

1. **Trigger** — when is it applicable?
2. **Method** — what should the agent inspect or test?
3. **Evidence** — what can support PASS, WARN, or FAIL?
4. **Boundary** — what is the agent not allowed to conclude?
5. **Remediation** — what should change if the check fails?

Bad:

> Make sure authentication is secure.

Good:

> Enumerate account/session creation paths. Verify session identifiers are
> generated by the auth system, protected in transit/storage, rotated where
> required, and invalidated by the relevant logout/revocation flows.

## Stable check IDs

Use:

```text
SEC-AUTHZ-001
PRIV-TRACK-001
LEGAL-CLAIM-001
A11Y-KBD-001
PROD-DB-001
```

Never reuse an existing ID for a different meaning.

## Legal/compliance additions

Do not encode jurisdiction-specific rules as universal facts.

A legal-oriented PR should identify:
- jurisdiction/market applicability;
- authoritative source to verify at execution time when rules can change;
- what can be verified from code/product behavior;
- what needs owner confirmation or counsel.

## Pull request checklist

- [ ] Directory name and `name:` match.
- [ ] `name:` is lowercase kebab-case and <= 64 chars.
- [ ] Description clearly states capability and triggers.
- [ ] `SKILL.md` stays focused; dense knowledge is in `references/`.
- [ ] New checks have stable IDs.
- [ ] PASS criteria are explicit.
- [ ] False-positive conditions are documented.
- [ ] Unknown facts remain unknown.
- [ ] Findings never require printing secrets or personal data.

## 2. WIP-190 — Deterministic skill validation

### Scope and files

```text
skills/i-do-not-want-my-website-to-die-in-production/SKILL.md
```

The six `SKILL.md` files will convert existing backtick-only reference paths into actual Markdown links so dependencies become machine-verifiable.

### Skill structure rules

Every direct child of `skills/` must contain `SKILL.md`, begin with delimited YAML frontmatter, and have frontmatter that parses as a mapping. Its string `name` must equal the directory name, use lowercase ASCII letters, digits, and single hyphens, contain no leading/trailing/consecutive hyphens, and contain at most 64 characters.

Malformed or structurally unverifiable input must produce diagnostics and a nonzero exit code.

### Local Markdown dependency rule

A local Markdown dependency is an inline Markdown link in `SKILL.md` whose destination is relative to that `SKILL.md`, has a path component ending in `.md`, may include a fragment, does not begin with `/`, and does not use a URI scheme.

The validator will resolve paths relative to the source file, strip fragments before checking existence, reject paths that escape the containing skill directory, ignore HTTP/HTTPS links, anchor-only destinations, images, fenced code, and inline code, and never treat arbitrary `.md` text as a dependency.

Repository dependencies use canonical inline syntax:

```markdown
[descriptive reference name](references/example.md)
```

Unsupported or malformed syntax that appears intended to declare a local Markdown dependency must fail closed. Missing-dependency diagnostics identify the source `SKILL.md`, referenced destination, normalized path when available, and reason.

### Canonical stable check declarations

A stable check ID is declared only when all these conditions hold:

1. The file is under `skills/*/references/*.md`.
2. The declaration occurs beneath `## Checks` and before the next heading of equal or higher level.
3. The line is a Markdown list item beginning with a backticked stable ID.
4. The ID follows the existing uppercase `DOMAIN-TOPIC-NNN` structure.
5. The declaration is outside fenced code blocks.

Example:

```markdown
## Checks

- `SEC-AUTHZ-001` BLOCKER: description
```

Only canonical declarations participate in duplicate detection. Examples, reports, manifests, fenced code, prose references, cross-references, and repeated references do not count. `docs/authoring.md` documents this rule.

### Tests and commands

Temporary fixture trees cover valid skill, missing `SKILL.md`, malformed YAML, non-mapping frontmatter, name mismatch, invalid kebab-case, names over 64 characters, missing local dependencies, ignored external and anchor links, ignored fenced and inline code, duplicate canonical declarations, and repeated non-declaration references.



It runs the Minitest suite and repository validator. `actions/checkout` is pinned to an immutable commit SHA with a comment naming the upstream release. No package installation is required.

## 4. WIP-192 — Machine-readable audit contract

### Scope and files

Add a JSON Schema Draft 2020-12 contract without replacing the human contract.

Create:

```text

```

Modify:

```text
docs/audit-contract.md
docs/roadmap.md
README.md
```

### Tooling

Use exactly pinned Ajv 8.17.1:

```json
"devDependencies": {
  "ajv": "8.17.1"
}
```

Use `Ajv2020` from `ajv/dist/2020.js` with `strict: true` and `allErrors: true`. Context7 confirms Ajv 8.17.1 supports draft-specific constructors, strict checking, and aggregated errors. Commit `package-lock.json`; use `npm ci`.

### Contract semantics

Top-level required fields are `contractVersion`, `target`, `evidenceMode`, `findings`, and `shipDecision`.

Each finding requires `checkId`, `domain`, `status`, `rationale`, `verification`, and `limitations`. `severity`, `evidence`, and `remediation` are optional or conditionally required so the existing conceptual report can represent `NOT_VERIFIED` without inventing severity.

Status remains exactly `PASS`, `WARN`, `FAIL`, `BLOCKED`, `NOT_APPLICABLE`, or `NOT_VERIFIED`. Severity remains exactly `BLOCKER`, `HIGH`, `MEDIUM`, `LOW`, or `INFO`. They remain independent.

For `PASS`, `WARN`, and `FAIL`, `evidence` must contain at least one valid entry. At minimum, the schema directly enforces that absent or empty evidence makes `PASS` invalid. Evidence uses a small kind vocabulary aligned with the existing hierarchy, a nonempty location/provenance reference, and an optional bounded summary.

Verification uses no number. Its intentionally small method vocabulary is `runtime-observation`, `test-result`, `configuration-review`, `source-review`, `manifest-review`, `documentation-review`, and `user-confirmation`. Method records provenance, not certainty, and cannot convert insufficient evidence into PASS. `NOT_VERIFIED` remains a status and requires a nonempty limitation.

### Versioning

Initial `contractVersion` is `1.0.0`. The stable, major-versioned `$id` is:

```text
https://raw.githubusercontent.com/radityprtama/i-do-not-want/main/schemas/audit-report-v1.schema.json
```

Adding optional fields is compatible; consumers ignore unknown optional fields. Required-field additions, removals, renames, meaning changes, and enum removals are breaking. Enum additions require a minor version and must not be interpreted as PASS by older consumers. Breaking changes require a new major contract version, schema file, and `$id`. Documentation-only clarification is a patch.

### Examples and commands

`examples/audit-report.v1.json` represents the existing human report's `SEC-AUTHZ-001`, `LEGAL-CLAIM-001`, `PRIV-TRACK-001`, `A11Y-AT-001`, and `DO_NOT_SHIP`. `render-audit-report.mjs` generates `examples/example-report.generated.md` from it.

Invalid fixtures prove PASS without evidence, unsupported status, and unsupported severity fail.

```bash
npm ci
npm run validate:reports
npm run render:report -- --check
npm run validate
```

The root `validate` script runs all Ruby tests/validators, schema validation, and generated-report drift checking.

### Acceptance, commit, and Linear

Acceptance requires Draft 2020-12 identification, successful Ajv validation, intended invalid-example failures, enforced PASS evidence, documented nonnumerical verification, preserved vocabulary, conceptually matching examples, version policy, and passing full validation.

Commit:

```text

```

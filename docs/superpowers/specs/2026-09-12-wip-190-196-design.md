# WIP-190–WIP-196 Hardening Design

## Scope

Deliver WIP-190 through WIP-196 sequentially, excluding WIP-195 and WIP-207. WIP-194 is already complete and receives no repository change. Every implemented original issue receives its own commit before work starts on the next issue.

Where an original issue combines local repository work with an unavailable external action, narrow the original to the verified local deliverable, create a linked follow-up for the external action, and close the original only after its narrowed acceptance criteria pass. This keeps the board clean without claiming that an unperformed action was verified.

## WIP-190: skill structure validation

Add a deterministic, dependency-free Ruby validator because Ruby's standard library provides YAML parsing while avoiding a package-install step in CI. The validator will:

- require `SKILL.md` in every direct `skills/*` directory;
- parse YAML frontmatter and reject malformed or non-mapping data;
- require the frontmatter `name` to match its directory, use valid lowercase kebab-case, and contain no more than 64 characters;
- resolve local Markdown paths referenced by each `SKILL.md` and reject missing files;
- identify stable check declarations in skill reference check lists and reject duplicate IDs;
- produce deterministic, actionable errors and a nonzero exit status.

Tests will exercise valid and invalid temporary fixture trees. A GitHub Actions workflow will expose one job named `validate`, and maintainer documentation will show the exact local command.

The branch-protection requirement moves to a linked follow-up: require `validate` in the existing `Protect main` ruleset after the workflow has completed successfully on GitHub.

## WIP-191: deliberately broken Next.js fixture

Add a clearly synthetic fixture under `fixtures/broken-nextjs/`. It will be valid enough for repeatable source audits while deliberately containing documented examples of all ten requested failure classes. Placeholder credentials will be unmistakably fake and nonfunctional.

An expected-findings manifest will map each seeded case to an existing stable check ID, source location, expected status/severity, and short rationale. Fixture documentation will state that vulnerable code must never be deployed or copied into production.

Use current Next.js App Router conventions confirmed through Context7. Keep the fixture small and avoid unrelated application functionality.

## WIP-192: machine-readable report contract

Add a versioned JSON Schema using JSON Schema Draft 2020-12. The schema will preserve the existing status and severity vocabularies as independent fields and model evidence locations, rationale, remediation, confidence/verification, and limitations.

Provide:

- a valid machine-readable report representing the same conceptual audit as the human example;
- invalid examples demonstrating that absent evidence cannot encode `PASS` and that vocabulary is constrained;
- a local validation command;
- compatibility rules defining additive versus breaking changes and the contract-version policy.

Use Context7 for current JSON Schema validator behavior and schema-loading guidance. Do not redesign the human vocabulary.

## WIP-193: Codex behavioral compatibility

Narrow this issue to the available Codex host. Record the exact Codex version and execution date. Exercise:

- explicit invocation of every domain skill;
- root-orchestrator routing;
- progressive reference loading;
- consistent report vocabulary;
- audit-only non-mutation, proven by repository or fixture hashes before and after execution.

Store reproducible commands and summarized evidence without committing sensitive transcripts. Any capability that cannot be evidenced remains `NOT_VERIFIED`.

Create a linked follow-up for equivalent Claude Code and OpenCode behavioral verification.

## WIP-196: launch-kit preparation

Narrow this issue to preparing a launch kit; do not publish. Add:

- a short problem-first post;
- a longer technical post;
- copy-paste install and destination links;
- a request for fixture contributions and false-positive reports;
- a shareable terminal-capture asset derived from reproducible fixture evidence;
- a channel checklist that discourages spam;
- a seven-day measurement template for referrals, stars, installs, issues, and meaningful feedback.

Create a linked follow-up for publication and the seven-day measurement window. Claims in launch copy must remain bounded by repository evidence.

## Linear workflow

For each issue, in order:

1. implement and verify the narrowed repository deliverable;
2. commit using the issue identifier in the commit subject;
3. create any specified follow-up issue and link it to the original;
4. update the original description to make the narrowed scope explicit;
5. move the original to Done.

Do not alter WIP-194, WIP-195, or WIP-207.

## Error handling and testing

Validators must fail closed, print file-specific diagnostics, and return nonzero for malformed input. Fixture and report examples must be checked by automated tests or validation commands. Codex compatibility evidence must distinguish observed behavior from limitations. Before each issue closes, run the smallest relevant checks plus the full repository validation available at that point.
